1.  AI MODULE — GROQ API INTEGRATION
    File: server/ai/groq.ts  (171 lines, NEW FILE)
────────────────────────────────────────────────────────────────────────────────

This is the core AI infrastructure module — a complete TypeScript HTTP client
for the Groq API (groq.com), which is a cloud-hosted LLM inference provider
offering high-speed access to open-weight models.

1.1  Type Definitions
- ChatMessage: { role: "user" | "assistant", content: string }
  This is the minimal public-facing message type accepted from the frontend.

- ConversationEntry: { role: string; content?: string; tool_calls?: unknown[];
  tool_call_id?: string } — A richer internal type used to build the full
  conversation array sent to the Groq API, including system prompts, tool
  calls from the assistant, and tool results pushed back into the
  conversation.

- GroqResponseMessage: { role: string; content: string | null;
  tool_calls?: Array<{ id: string; function: { name: string; arguments: string } }> }
  Maps the shape of the response from Groq's /v1/chat/completions endpoint.
  The tool_calls array contains function call objects generated by the LLM
  when it decides to invoke a tool rather than produce text directly.

- ChatResult: { content: string; toolCallsUsed: string[]; products: ChatProductCard[] }
  The final return type after a complete chat interaction. Contains the
  assistant's final text response, a list of tool function names that were
  invoked during the interaction, and any product cards that should be
  rendered alongside the response.

1.2  Configuration Constants
- GROQ_BASE_URL: "https://api.groq.com/openai/v1"
  This is the Groq cloud API endpoint. It is OpenAI-compatible, meaning the
  same message format and endpoint structure works — a deliberate design
  choice to allow easy model/provider swapping without changing the chat
  format.

- DEFAULT_MODEL: "meta-llama/llama-4-scout-17b-16e-instruct"
  The primary LLM model used for chat, tool calling, and completions. This is
  Meta's Llama 4 Scout with 17 billion parameters and 16 experts (MoE
  architecture). This model was specifically chosen for its strong
  instruction-following, native function-calling support, and fast inference
  speeds on Groq's LPU hardware.

1.3  API Key Management
- getApiKey(): Reads the GROQ_API_KEY environment variable from process.env.
  Throws a descriptive error if the variable is missing, preventing silent
  failures. The API key is loaded only when the GroqClient singleton is first
  instantiated.

1.4  GroqClient Class
This is the central HTTP client class that encapsulates all communication
with the Groq API. It maintains the API key and base URL as private instance
fields and exposes three primary methods.

Method: chatCompletion()
  - Signature: async (messages, options?) → Promise<GroqResponseMessage>
  - This is the low-level method that makes a raw HTTP POST to
    {baseUrl}/chat/completions.
  - Builds a request body with: model, messages array, temperature (default
    0.7), max_tokens (default 1024), tools (the full tool definitions array),
    and tool_choice: "auto".
  - The "auto" tool_choice lets the LLM decide whether to produce text or
    invoke a tool based on the user's query — no forced tool usage.
  - If options.useTools is set to false (used by generateCompletion and
    generateJsonCompletion), tools are excluded from the body entirely,
    allowing plain text or JSON generation without tool interference.
  - If options.responseFormat is provided (e.g., { type: "json_object" } for
    structured JSON output), it is added to the request body.
  - Uses the native fetch() API (available in Deno) to make the HTTP request.
  - Sets Content-Type to application/json and Authorization to Bearer {key}.
  - On error response (non-2xx), reads the response text and throws an Error
    with the HTTP status and body included for debugging.
  - On success, parses the JSON response and extracts choices[0].message.

Method: chat()
  - Signature: async (messages: ChatMessage[]) → Promise<ChatResult>
  - This is the primary chat method used by the AI router's chat endpoint.
  - Constructs the conversation array starting with a system message (the
    SYSTEM_PROMPT from system-prompt.ts) followed by all user and assistant
    messages from the chat history.
  - Calls chatCompletion() to get the assistant's first response.
  - Implements a TOOL CALLING LOOP: if the assistant's response contains
    tool_calls (i.e., the LLM decided it needs to look something up or
    perform an action), the code enters a loop (maximum 5 rounds):
    a. Pushes the assistant's response (with its tool_calls) into the
       conversation array.
    b. Calls executeToolCalls() from tools.ts, passing the tool calls and a
       callback (pushToConversation) that the executor uses to push each
       tool's result back into the conversation as a "tool" role message.
    c. Tracks the names of executed tools in toolCallsUsed[].
    d. Collects any product cards extracted from tool results into
       allProducts[].
    e. Makes another chatCompletion() call so the LLM can process the tool
       results and either produce a final text response or invoke more tools.
  - The loop has a hard limit of 5 rounds to prevent infinite tool-calling
    loops and control API costs.
  - Falls back to a graceful apology message if the LLM returns no content
    after all rounds: "I apologise, I was unable to process that. Could you
    rephrase?"

Method: generateCompletion()
  - Signature: async (prompt, options?) → Promise<string>
  - A simpler interface for text generation without chat history or tools.
  - Calls chatCompletion() with useTools: false, wrapping the prompt in a
    single user message (no system prompt).
  - Useful for one-shot tasks like product description generation.
  - Returns the message content, defaulting to empty string if null.

Method: generateJsonCompletion<T>()
  - Signature: async <T>(prompt, fallback, options?) → Promise<T>
  - A specialized method for structured JSON output generation.
  - Calls generateCompletion() with responseFormat: { type: "json_object" }
    which instructs the Groq API to ensure the output is valid JSON.
  - Uses a lower default temperature (0.3) for more deterministic output —
    important when the result needs to be machine-parseable.
  - Max tokens is set to 400 by default, sufficient for the JSON objects
    generated (smart search analysis, dashboard insights, etc.).
  - Wraps JSON.parse() in a try-catch: if parsing fails (the LLM produced
    malformed JSON), the fallback value is returned instead of crashing.
  - The generic type parameter T lets callers define the expected shape of
    the parsed JSON, providing type safety at the call site.

1.5  Singleton Pattern
- A module-level clientInstance variable holds the singleton GroqClient.
- getGroqClient(): Returns the existing instance or creates a new one.
  This ensures only one HTTP client exists, avoiding redundant API key
  loading and allowing connection reuse across multiple requests within
  the same server process.

1.6  Exports
- Named exports: GroqClient class for testing/custom usage.
- Type exports: ChatMessage, ConversationEntry, GroqResponseMessage,
  ChatResult — for use by consumer modules (routers, tools).

  - Plastic Cups (PC series): 59 designs, priced Rs 40-530 by size (5-44

2.3  Critical Behavior Rules (6 rules)
  1. ALWAYS call search_products or get_product_details when the user asks
     about specific products, wants to see products, or asks "which is best".
     Never answer from memory (prevents hallucination of product details).
  2. Never claim a product is unavailable unless the database confirms it.
  3. Never narrate actions — no "Let me search", "Searching", "Results:",

  4. No markdown tables. No numbered lists unless there are 3 or more items

  6. Product names in bold only. No fluff phrases like "Feel free to" or
     "Would you like to".

  Indian mobile), organization (optional), product interest, quantity, size,
  customization needs.
- Uses the submit_enquiry tool to persist the enquiry.

3.  AI TOOL SYSTEM — FUNCTION CALLING INFRASTRUCTURE
    File: server/ai/tools.ts  (391 lines, NEW FILE)
────────────────────────────────────────────────────────────────────────────────

This file implements the complete function-calling (tool-use) system that
enables the Groq-powered LLM to interact with the application database and
perform real actions beyond text generation.

3.1  Tool Definition Types
- ToolDefinition: Follows the OpenAI function-calling spec with:
  - type: "function"
  - function: { name, description, parameters (JSON Schema with properties,
    types, descriptions, and required fields) }

- GroqToolCall: Maps the tool call object returned in the LLM response:
  - id: string (unique call identifier for matching responses)
  - function: { name: string, arguments: string (JSON-encoded) }

3.2  Tool Registry (5 Tools Defined)

Tool 1: search_products
  Description: Search for products in the Delta Industries catalog by name,
  material, category, or keywords.
  Parameters:
    - query (string, required): Search query — product name, material, or
      keywords.
    - category (string, optional): Filter by category slug.
    - limit (number, optional): Max results (default 5, max 10).
  Implementation: Queries the database using Prisma's findMany with OR
  conditions across name, material, shortDesc, and category.name. Uses
  case-insensitive "contains" matching. Falls back to an empty result
  message when no products match.

Tool 2: get_product_details
  Description: Get complete details for a specific product by code (WA-06,
  PC-20) or slug (wooden-award-wa-06).
  Parameters:
    - slug (string, required): Product slug or identifier.
  Implementation: First tries an exact slug match via findUnique. If that
  fails, implements a FUZZY SEARCH fallback: converts the slug to
  searchable terms (replacing hyphens with spaces) and uses findMany
  with OR conditions on name and slug. If exactly one match is found,
  returns it. If multiple matches, returns a "multiple: true" result
  so the AI can disambiguate. Returns deep product data including all
  sizes with prices, MOQ, stock status, and all associated images.

Tool 3: get_categories
  Description: List all product categories available at Delta Industries
  with their descriptions.
  Parameters: None (empty properties object).
  Implementation: Queries all active categories ordered by sortOrder,
  returning id, name, slug, and description for each.

Tool 4: get_featured_products
  Description: Get featured/popular products for recommendations.
  Parameters: None (empty properties object).
  Implementation: Queries up to 6 products where isActive and isFeatured
  are true, ordered by viewCount descending. Includes the cheapest size
  for a price hint.

Tool 5: submit_enquiry
  Description: Submit a customer enquiry/order request to Delta Industries.
  Parameters:
    - customerName (string, required): Full name.
    - email (string, required): Email address.
    - phone (string, required): Indian mobile number (10 digits).
    - organization (string, optional): Organization/school/company.
    - message (string, required): Summary of requirements.
    - quantity (number, optional): Approximate quantity needed.
    - productId (number, optional): Database product ID.
  Implementation: Creates an Enquiry record in the database via Prisma.
  Returns the enquiry ID and a confirmation message stating Delta will
  contact within 24 hours.

3.3  executeTool() Function
- A central dispatcher function with a switch statement over tool names.
- Each case handles one tool, extracting typed arguments from the
  generic Record<string, unknown> args parameter.
- All results are returned as JSON strings — this is the format the LLM
  receives when tool results are fed back into the conversation.
- Includes a default case returning an error for unknown tool names.

3.4  Product Data Extraction — extractProductsFromToolResult()
- Type: ChatProductCard: { id, name, slug, category, material, shortDesc,
  imageUrl, priceHint }
- This function parses JSON tool results and extracts product data for
  rendering as product cards in the chat UI.
- Handles three tool result formats:
  - Multiple products via results.products array (search, featured).
  - Single product via results.product object (get_product_details).
  - Falls through returning empty array for non-product tools.
- For price hints, it checks for a priceHint field first, then falls back
  to the first size's priceRange, then to null.

3.5  Tool Call Execution Loop — executeToolCalls()
- Signature: async (toolCalls, pushToConversation) → { executed, products }
- Iterates over each tool call in the LLM's response.
- For each tool call:
  a. Parses the function.arguments JSON string. If parsing fails, proceeds
     with an empty args object (graceful degradation).
  b. Calls executeTool() with the tool name and parsed args.
  c. Records the tool name in the executed[] array.
  d. Calls extractProductsFromToolResult() for any product cards.
  e. Uses the pushToConversation callback to push a "tool" role message
     back into the conversation with the JSON result string and the
     tool_call_id for LLM context matching.
- Returns both the list of executed tool names and all extracted products.

4.  AI-tRPC ROUTER — 5 AI-POWERED ENDPOINTS
    File: server/routers/ai.ts  (184 lines, NEW FILE)
────────────────────────────────────────────────────────────────────────────────

This file defines the tRPC router for all AI-related endpoints, integrating
the Groq AI client with the application's database and business logic.

4.1  Input Schemas (Zod Validation)
All inputs are validated with Zod schemas to enforce type safety at the API
boundary:

- chatMessageSchema: { role: z.enum(["user", "assistant"]), content: z.string() }
- chatInput: { messages: z.array(chatMessageSchema).min(1).max(30) }
  Enforces that at least 1 and at most 30 messages are sent per chat request.
  This prevents excessively large payloads.

- generateDescriptionInput: { name: z.string().min(1).max(200),
  material: z.string().max(100).optional(),
  category: z.string().max(100).optional() }

- smartSearchInput: { query: z.string().min(1).max(200) }

- similarProductsInput: { productSlug: z.string().min(1) }

- dashboardInsightsInput: { totalEnquiries: z.number(),
  newEnquiries: z.number(),
  recentProducts: z.array(z.object({ name: z.string(), views: z.number() })),
  recentEnquiryMessages: z.array(z.string()) }

4.2  Endpoint: chat
- Type: Mutation (POST-like)
- Input: chatInput (array of chat messages)
- Behavior:
  1. Gets the singleton GroqClient instance.
  2. Calls groq.chat() with the user's messages.
  3. Returns an object containing:
     - content: The assistant's final text response.
     - toolCallsUsed: Array of tool names invoked during the interaction
       (e.g., ["search_products", "get_product_details"]).
     - products: Array of ChatProductCard objects extracted from tool
       results, for rendering product suggestions in the chat UI.

4.3  Endpoint: generateDescription
- Type: Mutation
- Input: generateDescriptionInput (product name, material, category)
- Behavior:
  1. Constructs a detailed prompt instructing the AI to write a
     professional, SEO-optimized product description (2-3 paragraphs,
     150-250 words).
  2. Includes requirements: highlight craftsmanship, mention use cases
     (events, ceremonies, occasions), describe visual appeal and finish,
     note customization options, formal tone, no emojis.
  3. Calls groq.generateCompletion() with temperature 0.8 (some
     creativity) and maxTokens 512.
  4. Returns { description: string } — the plain text description.

4.4  Endpoint: smartSearch
- Type: Mutation
- Input: smartSearchInput (natural language query string)
- Behavior:
  1. Constructs a detailed prompt asking the AI to analyze the search query
     and classify it into structured dimensions:
     - interpretedAs: Brief human-readable interpretation.
     - category: Matching category slug from a predefined list (wooden-
       trophies, acrylic-awards, metal-cups-trophies, crystal-trophies,
       plastic-trophy-series, custom-medals, trophy-bases-accessories,
       corporate-gift-mementos, shields-plaques) or null.
     - material: Detected material (wood/metal/acrylic/crystal/plastic/
       brass/marble) or null.
     - budget: Price tier (budget/mid-range/premium) or null.
     - useCase: Event type (sports/academic/corporate/school/wedding/
       government) or null.
     - size: Size category (small/medium/large) or null.
     - keywords: Extracted search terms array.
  2. Calls groq.generateJsonCompletion<SmartSearchResult>() — the generic
     type parameter provides both the return type and the fallback shape.
  3. The fallback simply passes the original query through.
  4. This structured analysis is used by the frontend search page to:
     - Display an "AI understood your search as..." interpretation.
     - Show filter chips for category, material, budget, and use case.
     - Augment the search query with extracted keywords for better
       database matches.

4.5  Endpoint: similarProducts
- Type: Mutation
- Input: similarProductsInput (product slug)
- Behavior:
  1. Looks up the source product by slug to get its category ID.
  2. If the product is not found, returns empty recommendations.
  3. Finds up to 4 products in the same category (excluding the current
     product), ordered by viewCount descending.
  4. Returns:
     - sourceProduct: { name, category, material }
     - recommendations: Array of similar products with id, name, slug,
       category, material, shortDesc, imageUrl, priceHint.
  5. This is used on the ProductDetail page to show a "Similar Products"
     section below the main product details.

4.6  Endpoint: dashboardInsights
- Type: Mutation
- Input: dashboardInsightsInput (enquiry statistics and recent data)
- Behavior:
  1. Constructs a prompt with analytics data:
     - Total enquiries count
     - New (unread) enquiries count
     - Recent product views (name + view count)
     - Recent enquiry subject lines
  2. Instructs the AI to generate 3-4 actionable business insights and a
     one-sentence summary.
  3. Calls groq.generateJsonCompletion<InsightsResult>() with a fallback
     of ["AI insights unavailable right now."].
  4. Returns { insights: string[], summary: string } for display in the
     admin dashboard.

4.7  Router Registration
In server/routers/index.ts, the aiRouter is added to the main app router
under the "ai" namespace:
  ai: aiRouter
This makes all 5 endpoints available as: trpc.ai.chat, trpc.ai.smartSearch,
trpc.ai.generateDescription, trpc.ai.similarProducts, trpc.ai.dashboardInsights.

5.  MEILISEARCH / DATABASE SEARCH ENGINE
    File: server/meilisearch.ts  (107 lines, MODIFIED)
────────────────────────────────────────────────────────────────────────────────

This file has been significantly reworked from its original Meilisearch
integration to a SUPABASE/POSTGRESQL-BASED SEARCH using Prisma ORM's
built-in "contains" text matching.

5.1  Search Architecture Change
The original Meilisearch dependency was removed. The new implementation
uses PostgreSQL full-text search capabilities through Prisma's query
builder. This eliminates the need for a separate Meilisearch service,
reducing infrastructure complexity and operational costs.

5.2  ProductSearchResult Interface
Exports a typed interface for search results with 17 fields:
  id, name, slug, categoryName, categorySlug, material, shortDesc,
  description, imageUrl, isCustomizable, isFeatured, viewCount,
  sizeLabel, priceMin.

5.3  searchProducts() Function
- Takes a query string and optional filter parameters (categorySlug,
  limit, offset).
- Implements WORD-BASED MATCHING: splits the query into individual words
  (minimum 2 characters each), then constructs OR conditions across
  five text fields for each word:
  - product name
  - material
  - short description
  - full description
  - category name
- This multi-word matching means searching for "golden trophy" will match
  products that have "golden" in the material AND "trophy" in the name.
- Category filtering: when a categorySlug is provided, adds an additional
  where clause for category.slug equality.
- Sorting:
  1. isFeatured descending (featured products first)
  2. viewCount descending (popular products first)
  3. Name ascending (alphabetical tiebreaker)
- Runs product query and count query in parallel using Promise.all() for
  performance.
- Pricing: extracts the cheapest size's priceMin for display, converting
  from Prisma's Decimal type to a JavaScript number.
- Processing time is measured and returned for observability.
- Returns: { hits[], estimatedTotalHits, processingTimeMs }.

5.4  No-Op Stubs for Backward Compatibility
configureProductIndex() and indexProducts() are kept as no-op stubs that
log "[supabase-search] Using PostgreSQL full-text search" messages. These
preserve the API shape for any scripts or tests that may call them but
perform no actual work since PostgreSQL search is always real-time.

6.  DEVELOPMENT SCRIPTS & BUILD INFRASTRUCTURE
────────────────────────────────────────────────────────────────────────────────

6.1  scripts/dev-all.mjs  (MODIFIED — Changed from 9 to 7 active lines)
Changed the spawn command to use 'concurrently' to run both:
  - "node scripts/dev-frontend.mjs" (frontend Vite dev server)
  - "npm:dev:server" (Deno backend server)
This replaced a previous approach that may have used separate terminal
windows or sequential startup. The new approach uses a single terminal with
concurrently for unified log output.

6.2  scripts/dev-frontend.mjs  (NEW FILE — 21 lines)
A specialized frontend development server launcher that:
  a. Computes the project root directory (parent of scripts/).
  b. Unsets the DENO_DIR environment variable to prevent Deno from
     interfering with Node.js module resolution (critical fix for
     mixed Deno+Node projects where Deno's module cache can shadow
     node_modules).
  c. Waits 3 seconds (setTimeout 3000ms) before launching Vite, giving
     the Deno backend server time to start listening on port 3001.
     This prevents Vite's proxy from encountering ECONNREFUSED errors
     when it tries to forward /trpc requests to a backend that hasn't
     started yet.
  d. Spawns Vite as: node ./node_modules/vite/bin/vite.js with the
     project root as CWD and the cleaned environment.
  e. Propagates Vite's exit code to the parent process.

6.3  Vite Configuration Updates (vite.config.ts)
Several important changes to the development server:
  - Port changed to 8080 (from potentially a different port).
  - HMR overlay disabled (overlay: false) to prevent error overlays from
    covering the UI during development.
  - Proxy configuration for /trpc requests:
    * Target: http://localhost:3001 (the Deno backend server port).
    * Cookie forwarding: proxyReq handler copies cookies from the browser
      request to the backend request, enabling session-based auth to work
      through the proxy.
    * Cookie rewriting: proxyRes handler strips "Secure" and "SameSite=None"
      flags from set-cookie headers since the dev server runs on HTTP
      (localhost is not HTTPS), preventing browsers from rejecting
      cookies.
  - Resolve aliases: "@" → "./src" (path alias for clean imports).
  - Deduplication: react and react-dom are deduplicated to prevent
    multiple React instances in the bundle.
  - Optimize deps: react, react-dom, @tanstack/react-query, and
    @trpc/react-query are included in optimizeDeps for faster cold
    starts with Vite's dependency pre-bundling.
  - Added lovable-tagger plugin (componentTagger) that runs only in
    development mode (mode === "development" check with filter(Boolean)).
